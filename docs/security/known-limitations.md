# Known Security Limitations

Dovepeak Identity documents its limitations openly (problem statement §16: "Security limitations and supported flows are documented honestly"). Each item states the impact, the current mitigation and the plan.

Last reviewed: 2026-10-10 (Phase 6, before version 1.0). Resolved items stay listed, struck through, so the history is visible.

| # | Limitation | Impact | Current mitigation | Plan |
| - | ---------- | ------ | ------------------ | ---- |
| L-01 | **Access token revocation is not instant** for resource servers that validate JWTs locally. | A revoked session's access token stays usable for up to its lifetime (default 10 minutes). | Short access token lifetime; optional introspection for sensitive APIs (ADR-0003). | SDK introspection mode (M5.3, M5.4). |
| L-02 | **JWKS caching delays emergency key rotation** at resource servers. | Old access tokens accepted until the resource server refreshes its key cache. | Runbook step 2.3 (restart or refresh resource servers); the SDKs cache keys for at most 10 minutes and refetch on an unknown key ID (`SigningKeyRotationTests`, `node.test.ts`). | Accepted. |
| L-03 | **Idle session timeout has a 2-minute grace window** (Keycloak behaviour). | Idle sessions end up to 2 minutes later than configured. | Absolute lifetime is exact. | Accepted. |
| ~~L-04~~ | ~~No per-account email throttling.~~ **Resolved in Phase 6.** | — | All email passes through the Dovepeak mail relay: at most 5 per recipient per hour and 20 per day, 500 per tenant per hour; excess dropped silently so the response does not reveal the account (`PasswordRecoveryTests`, `RelayTests`). | — |
| L-05 | **No breached-password check** (e.g. Have I Been Pwned). | Users can choose a long password that is known to be breached. | Minimum length 12, password history, not-username, not-email, Argon2 hashing, brute-force lockout. | Evaluated in Phase 6: needs a Keycloak extension (Java) or an external call during registration; deferred to after 1.0. |
| L-06 | **Refresh token reuse revokes the client session, not the SSO session.** | After detected theft, the user's browser SSO session survives. | The attacker holds refresh tokens, not the SSO cookie; the stolen token family is dead. | Accepted (ADR-0003). |
| L-07 | **Tenant branding is limited to a logo, one colour and email wording.** Layout, fonts and full template control are not customisable. | Tenants with strict brand guidelines may need more. | Logo (HTTPS), brand colour with automatic readable text, custom subjects and introductions; links and footer stay platform-controlled to prevent phishing (ADR-0010). | Uploaded logos and more style options if customers need them. |
| L-08 | **Realm provisioning slows as tenant count grows** (see Phase 1 validation report). | Slower onboarding at high tenant counts; not on the sign-in path. | Constant-size admin token; provisioning is asynchronous. | Shard tenants across Keycloak clusters at the measured threshold (ADR-0001). |
| L-09 | **The local development stack trusts all forwarded-header sources.** | Only the development stack; a client could spoof its IP there. | **Production deployment fixed (M6.5):** Caddy replaces untrusted forwarded headers, the edge trusts only Caddy's address and Keycloak only the edge's (`KC_PROXY_TRUSTED_ADDRESSES`); rate limits key on the real client address (verified in the production rehearsal). | Accepted for local development. |
| L-10 | **Audit collection is near-real-time, not synchronous.** | Events appear in the Dovepeak audit store after up to one poll interval (default 15 s). Keycloak retains events for 30 days as a buffer. | Idempotent, checkpointed collection. | Consider an event-listener extension if lower latency is required. |
| L-11 | **No independent penetration test yet.** | Unknown vulnerabilities may exist. | Automated security tests, API fuzzing (Schemathesis), load testing, CodeQL, dependency, container and secret scanning; threat model review (v0.4). | Independent test before external customers (M6.4); version 1.0 is not tagged until it is done and every critical and high finding is fixed. |
| L-12 | **Only the `default` identity-engine cluster is routed.** Each environment records its cluster, but the Management API, workers and edge talk to a single Keycloak deployment. | Realm count is bounded by one cluster (sharding threshold ~300 realms, Phase 1 validation report). | Cluster recorded per environment from day one; the sharding design and runbook exist ([tenant-sharding.md](../runbooks/tenant-sharding.md)) with an early-warning query at 80% of the threshold. | Multi-cluster routing before any deployment reaches 240 realms. |
| L-13 | **Overlapping client secret rotation depends on a Keycloak preview feature** (`client-secret-rotation`). The overlap is a fixed 24 hours for every application. | If a Keycloak upgrade changes or removes the feature, realm provisioning fails loudly (the template references it); rotation would then fall back to immediate replacement. | Enabled explicitly (`KC_FEATURES`); covered by `CredentialApiTests` and the drift tests, so an upgrade that breaks it fails CI. `revokePrevious` and `DELETE …/secret/previous` end the overlap at once after a leak. | Re-evaluate on every Keycloak upgrade; per-application overlap periods if customers need them. |
| L-14 | **A confidential client recreated by reconciliation gets a new secret.** Applies only when someone deletes the client directly in Keycloak. | The application stops authenticating until a developer rotates the secret and redeploys. | The admin API is not exposed publicly (ADR-0007); the recreation is audited and sent as a `drift.corrected` webhook. | Accepted: Dovepeak never stores client secrets (ADR-0004). |
| L-15 | **Keycloak's administrative role names cannot be application roles** (`admin`, `realm-admin`, `manage-users`, `view-*`, `query-*`, …). Keycloak only lets an admin grant these names if it holds the identical admin role, which the least-privilege management account does not. | Developers must pick another name (e.g. `administrator`). | Rejected at creation with a clear `400` (`ReservedRoleNames`), so no role exists that cannot be assigned. | Accepted. |
| L-16 | **The reference production deployment runs on one host.** Two Keycloak nodes protect against a failed Keycloak process, not against losing the server. | Host loss is an outage until a restore on a new host completes (RTO 1 hour). | Encrypted point-in-time backups to an off-site S3 repository; restore drills; [database failure runbook](../runbooks/database-failure.md), section 3. | A multi-host deployment (managed PostgreSQL, Keycloak nodes on separate hosts) when an operator needs higher availability than 99.9%. |
| L-17 | **Second factors are optional and untested.** Users can add a TOTP authenticator through Keycloak's account console; tenants cannot require it. | Accounts are protected by password and brute-force lockout only, unless users opt in. | Strong password policy, lockout, security alert emails. | Per-tenant MFA policy and automated tests after 1.0. |
| L-18 | **Telemetry redaction is verified manually, not in CI.** | A future change could record a query string or token in a trace without failing a test. | No query strings recorded at source; the collector strips query strings, `Authorization` and `Cookie`; manual scan of sign-in traces on 2026-10-10 found none. | Automated trace scan in the CI integration job. |
| L-19 | **Realms share one mail relay password.** | Someone with Keycloak admin access could make email count against another realm's quota. | Keycloak admin access is never public (ADR-0007) and every admin change is reverted by reconciliation; quotas only limit email, they do not grant access. | Per-realm relay credentials if tenants ever get admin access. |
